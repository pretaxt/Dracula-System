## 一、项目级别决策(3 项)

### **决策 1.1 · 月化收益预期 1%-3%**

#### 是什么
整套系统 Phase 0 阶段(资金 $5k-$30k)的**合理月化收益预期**,作为衡量"系统是否正常工作"的基准线。

#### 关键数字
- **差**:1% / 月($350 per $35k)
- **中**:2% / 月($700 per $35k)
- **好**:3% / 月($1,050 per $35k)
- **危险信号**:连续 3 个月 > 5%(说明你可能在加杠杆 / 偏离对冲策略)

#### 为什么这样设计
- 顶级 quant 基金(Renaissance、Two Sigma)长期年化 30%-40%(月化 ~2-3%)
- 加密 Delta 中性套利策略(资金费率、期现、基差)历史数据月化 1.5%-2.5%
- 散户做这类策略平均 0.5%-1.5%(执行差距、规模劣势)
- 我们目标 1%-3% 是**合理偏乐观**的预期

#### 不同意的后果
**如果你期待 10%+/月**:
- 你会感觉"系统不行" → 加大杠杆 / 缩短测试 / 跳过风控
- 这是该行业 80% 散户失败的原因
- 真实结果:2-3 个月内大概率爆仓

**如果你期待 0.5%/月**:
- 你会过早放弃 / 觉得"不值得做"
- 但实际上你可能已经赢了——只是没看到长期复利

#### 替代方案
- 接受更低预期(0.5%-1%)→ 更安全,但 12 周后看到 $200/月会沮丧
- 接受更高预期(3%-5%)→ 加杠杆,但风险指数级增加

#### 给"全职 + $35k"的具体建议
- 月化 2% × $35k = **$700/月**(Phase 0 末期)
- $700/月的收入**不够全职生活费** — 这是为什么我之前问你 runway 的原因
- 心理上准备好:**前 3-6 个月这个项目几乎没收入**,后面才有可能复利起来

### **决策 1.2 · 8-12 周开发周期**

#### 是什么
从今天到第一个策略**实盘上线**的预期时间。

#### 关键数字
- **乐观**:8 周(全职 + 顺利)
- **合理**:10 周(包含调试)
- **保守**:12 周(包含意外)
- **不要做的事**:< 6 周(必然跳过 paper trading)

#### 为什么这样设计

**8-12 周分配**(基于第 1 章路线图):
```
第 1-2 周:项目骨架 + 数据库 + 配置系统
第 3-4 周:第一个交易所适配器(Binance) + 资金费率扫描
第 5-6 周:风控引擎 + Position Manager
第 7-8 周:回测框架 + 第一个策略回测验证
第 9-10 周:Paper Trading 14+ 天
第 11-12 周:实盘 $500 stage 1 + 调优
```

每个阶段都不能跳。这是**最小完整链路**,缺一会出大问题。

#### 不同意的后果

**如果你想 4-6 周上线**:
- 必然跳过 paper trading
- 实盘第一周 80% 概率出大问题:
  - 订单失败处理不完善 → 卡仓
  - WS 断连 → 部分头寸丢失
  - 资金费率结算时机算错 → 实际收益 ≠ 预期
- 修 bug 时真金白银亏损

**如果你想 16+ 周稳健做**:
- 也许更稳,但全职情况下 $35k 可能撑不到那时
- 长时间不见结果会失去动力

#### 替代方案
- **激进路径**:跳过部分回测,先用真实小钱($100)测试 → 风险高
- **稳健路径**:每个阶段加 1 周缓冲 → 总共 16 周 → 资金压力大

#### 给"全职 + $35k"的具体建议
- **接受 10 周(中间值)**
- 第 5 周做一次 mid-review,如果落后 1 周以上,提前调整
- 不要因为"想早点开始赚钱"而压缩时间

### **决策 1.3 · 资金阶梯放大($500 → $1k → $2k → $5k)**

#### 是什么
实盘阶段**资金不能一次到位**,必须每个阶段验证后再加。每个阶段至少跑 14 天,通过后才进下一阶段。

#### 关键数字

```
Stage 1: $500    持续 14 天   验证执行链路
Stage 2: $1,000  持续 14 天   验证 2 交易所
Stage 3: $2,000  持续 14 天   验证多策略并行
Stage 4: $5,000  持续 30 天   Phase 0 目标
Stage 5: $10k+   Phase 1 阶段
```

#### 为什么这样设计

**风险控制的基本规律**:
- 系统的 bug 通常在前 2 周暴露
- 资金 10 倍小的时候,bug 暴露的成本也是 10 倍小
- $500 阶段如果有 bug,最多损失 $500
- 直接 $5k 上线如果有同样 bug,可能损失 $5k

**心理控制**:
- $500 阶段你不会因为浮亏 -3% 焦虑(亏 $15)
- $5k 阶段同样 -3% 浮亏(亏 $150)会让你做错决策

#### 不同意的后果

**如果你跳到 $2k 起步**:
- 第一次 bug 出现时,损失放大 4 倍
- 你的心理无法承受 → 紧急关停 → 系统未充分测试

**如果你 $5k 一次到位**:
- 一旦出大 bug → $200-$500 损失
- 你信心受挫,可能放弃整个项目

#### 替代方案
- **更细分**:$200 → $500 → $1k → $2k → $5k(更安全,但拖时间)
- **更激进**:$1k → $5k → $10k(我**不推荐**)

#### 给"全职 + $35k"的具体建议
- $35k 中只有 **$5k 进入实盘 Phase 0**
- 剩下 $30k **不要动**,等 Phase 1
- 如果你 Phase 0 阶段(8 周)月化没达到 1%,**不要进 Phase 1**(系统没准备好)

## 二、风控红线(3 项,**写死在代码里**)

### **决策 2.1 · 单日回撤红线 -3%**

#### 是什么
单日亏损超过总资金的 3% → **系统自动停机 + 平仓所有头寸 + 通知所有渠道**。

需要人工介入并修改 yaml + 重启系统才能恢复交易。

#### 关键数字

```
Phase 0 资金 $5k:
  红线 -3% = $150
  系统会触发停机

Phase 1 资金 $30k:
  红线 -3% = $900

警戒线(自动平仓阈值):
  Tier 1(可调):-1%
  Tier 2(延迟生效):-2%
  Tier 3(锁定红线):-3%
```

#### 为什么这样设计

**3% 是"不痛不痒到痛"的临界点**:
- < 1%:正常波动,不应触发任何保护
- 1%-3%:警戒区,Tier 1/2 提示但不强制
- **> 3%:必然有异常**(策略失效 / 系统 bug / 黑天鹅)

**对应到资金回撤**:
- -3% 单日 = 月度可能 -10% 到 -15%
- 这已经超过任何 Delta 中性策略的合理范围

#### 不同意的后果

**改成 -5% / -10%**:
- 黑天鹅时,你会从 -3% 看着它继续到 -10% 甚至 -20%
- 心理上无法在剧痛中做出冷静决策
- LUNA 崩盘时(2022 年 5 月)很多策略一天就 -50%

**改成 -1% / -2%**:
- 太敏感,正常波动也会触发
- 频繁停机 → 错过本可恢复的机会
- 心理上会"对系统失去信心"

#### 替代方案
- **分级红线**:-2% 警告 / -3% 暂停 / -5% 强制平仓 → 已经在这么做(Tier 1/2/3)
- **不设红线**:危险至极,**绝对不行**

#### 给"全职 + $35k"的具体建议
- 接受 -3%
- 知道这个红线意味着**你会经常看到系统暂停**(这是好事)
- 心理建设:**触发风控不是失败,是系统正常工作**

### **决策 2.2 · 永续杠杆永远 ≤ 3 倍**

#### 是什么
任何永续合约持仓的杠杆**写死在 config.yaml 中**,改它需要修改文件并重启系统。UI 上无法调整。

#### 关键数字

| 杠杆 | 清算价格距离 | 风险评估 |
|---|---|---|
| **1x** | 100% (永不清算) | 最安全 |
| **3x** | -33%(币价跌 33%) | 我们的设定 |
| 5x | -20% | 危险 |
| 10x | -10% | 极危险 |
| 20x+ | -5% | 自杀级 |

#### 为什么这样设计

**Delta 中性策略不需要高杠杆**:
- 资金费率套利:杠杆只是为了"用同等保证金做更大名义价值"
- 1 倍杠杆收 8% APR = 3 倍杠杆收 24% APR(看起来诱人)
- 但 3 倍杠杆下,**单边持仓被清算的概率高 9 倍**

**3 倍是"合理的杠杆":**
- 资金效率比 1x 提升 3 倍
- 单边币价跌 30% 才清算(罕见)
- 月化收益 1%-3% 已经够好

#### 不同意的后果

**改成 5-10 倍**:
- 表面收益翻倍
- 实际风险**指数级**增加
- 一次黑天鹅(如 519、312)直接清算
- 80% 加密散户的清算都是因为 5x+ 杠杆

**改成 1 倍**:
- 资金效率太低
- 月化可能从 2% 降到 0.7%
- 长期不值得做

#### 替代方案
- **可变杠杆**:不同币种不同杠杆 → 复杂,容易出错
- **动态杠杆**:根据波动率调整 → Phase 1 后再考虑

#### 给"全职 + $35k"的具体建议
- 接受 3 倍
- 心理上记住:**杠杆 ≠ 收益**。杠杆是放大风险的工具
- 如果你某天想"加到 5 倍试试",**先看一眼这份文档**

### **决策 2.3 · Tier 3 风控锁定(改 yaml + 重启才能修改)**

#### 是什么
最严的风控参数(单日回撤红线、保证金率、API 错误熔断)**不能在 UI 上修改**,必须:
1. 停止系统
2. SSH 到服务器
3. 编辑 `config/risk.yaml`
4. 重启系统

整个过程需要 5-10 分钟,**有意制造摩擦**。

#### 关键数字

**Tier 1**(随时改):扫描 APR、仓位规模、最大并发
**Tier 2**(改后 24 小时生效):单交易所占比、单币种占比
**Tier 3**(锁定):**单日回撤红线、杠杆上限、保证金率**

#### 为什么这样设计

**这是为了对抗"未来你"**。

举例:
- 某天系统连续 3 天亏损,触发 -3% 红线
- 当时的你:理性,会读日志,找根因
- 假设 Tier 3 可在 UI 改:你会想"今天行情特殊,临时关掉吧"
- 关掉之后:亏损扩大到 -10% / -20%
- LUNA 散户、FTT 散户、312 散户的剧本

**有意制造摩擦,让你"想改"和"真的改"之间隔 10 分钟冷静期**。

#### 不同意的后果

**Tier 3 可在 UI 改**:
- 你某天情绪化决策时能立刻改
- 这就是"为什么不该在 UI 上"
- 复盘时你会发现:"我那天不该改的"

**Tier 3 完全不可改**:
- 极端情况下需要修风控参数(如交易所 API 升级,旧阈值不适用)
- 完全不可改会导致系统僵化
- 所以保留"改 yaml + 重启"作为可控的修改通道

#### 替代方案
- **二次确认**:UI 上改但需要密码 → 不够,情绪化时密码也输得进去
- **冷静期**:UI 上改后 24 小时生效 → 已经是 Tier 2 的做法
- **完全锁死**:不能改 → 太僵化

#### 给"全职 + $35k"的具体建议
- 接受这个设计
- 想象一个场景:你某天连续亏 2 天,情绪低落
- 那一刻你**最想改的就是 Tier 3**
- 那一刻**也是最不该改的时刻**
- 这个设计就是为了保护那一刻的你

## 三、策略组合(2 项)

### **决策 3.1 · Phase 0 只跑 3 个策略,不跑 17 个**

#### 是什么
Phase 0 阶段(0-12 周,资金 $5k 实盘)实际上线运行的策略**只有 3 个**:
- #1 资金费率套利(主力,$2,000)
- #4 期现套利(辅助,$1,000)
- #13 三角套利(小额验证,$500)

其他 14 个策略**都是 Phase 1+ 阶段才考虑**。

#### 关键数字

**Phase 0 资金分配**($5k 实盘):
```
资金费率套利:    $2,000   (40%)  — 主力
期现套利:        $1,000   (20%)  — 互补
三角套利:        $500     (10%)  — 验证执行系统
储备金:          $1,500   (30%)  — 应急
```

**Phase 1 阶段**($30k+)再加:
- #2 跨所基差套利
- #16 配对交易
- #5 CEX-DEX 监控(无资金,只发推送)

#### 为什么这样设计

**核心原因:摊薄即失败**。

如果 17 个策略一起跑,$5k 摊到每个不到 $300:
- 每个策略持仓 < $100
- 单次手续费 0.1% = $0.10
- 单次预期收益 0.5% = $0.50
- **手续费成本占比太高,几乎赚不到钱**

**而且**:
- 17 个策略一起跑 = 17 倍代码复杂度 = 17 倍 bug 概率
- 你 8 周开发不可能让 17 个策略都达到生产质量
- "全做"= "全做不好"

**3 个策略的选择理由**:
- #1 资金费率:核心,最稳定,资金容量最大
- #4 期现套利:互补,不同时间尺度,跟 #1 风险无关
- #13 三角套利:训练系统执行能力(高频小额),验证整个工程链路

#### 不同意的后果

**如果你坚持上更多**:
- 8 周不够 → 时间被压缩 → 每个都不达标
- 资金分散 → 每个都赚不到钱
- 注意力分散 → 不知道哪个赚钱哪个亏钱

**如果你只上 1 个(资金费率)**:
- 单点失败风险:如果资金费率市场短期失效,你 0 收入
- 缺少验证:执行系统、风控等不会被充分压力测试

#### 替代方案
- **2 个策略**:#1 + #4,跳过三角套利 → 可以,但失去执行验证
- **5 个策略**:加 #2 + #5 监控 → Phase 0 后期可以,初期不要

#### 给"全职 + $35k"的具体建议
- 接受"只 3 个"
- $5k Phase 0 + $30k 储备
- 8 周后看 3 个策略表现:
  - 如果 3 个都不错 → 进 Phase 1,加策略
  - 如果 1-2 个不行 → 修复后再加
  - 如果都不行 → **重新评估这个项目**

### **决策 3.2 · 期权策略 Phase 0 默认禁用**

#### 是什么
#6 期权波动率套利策略**写在文档里但 yaml 中默认 `enabled: false`**。$30k+ 资金量才考虑启用,**且必须先进入"监控模式"**(模拟交易 30 天)。

#### 关键数字

| 策略类型 | 月度回撤上限 | 月度收益预期 |
|---|---|---|
| 资金费率套利 | -3% | +1.5% to +2% |
| 期现套利 | -3% | +1% to +1.5% |
| 三角套利 | -1% | +0.3% to +0.8% |
| **期权波动率** | **-30%** | +3% to +10% |

期权一个月的波动 = 其他策略全年波动。

#### 为什么这样设计

**期权是"放大版的赌博"**:
- 收益放大 5-10 倍 → 同时风险也放大 5-10 倍
- 数学复杂度高 10 倍(Greeks: Delta、Gamma、Theta、Vega...)
- 流动性差 10 倍(深 OTM 合约几乎无对手盘)
- 错误成本高 100 倍(一次方向看反就归零)

**Phase 0 阶段的你**:
- 资金 $5k,任何 -10% 都是真实痛感
- 经验不足,不能识别期权的所有陷阱
- 系统不稳定,bug 在期权策略上代价是其他策略的 10 倍

#### 不同意的后果

**如果你 Phase 0 启用期权**:
- 真实案例:某用户 $5k 做期权,2 周亏掉 $4k
- 心态崩 → 放弃整个项目

**如果你永久禁用期权**:
- 损失了一个高收益机会(Phase 2 阶段)
- 但远比"做错"好

#### 替代方案
- **Phase 0 监控模式**:启用,但只看不做(发推送给你) → 可以
- **Phase 0 1% 资金试**:$50 试期权 → 学习成本太高,不值得

#### 给"全职 + $35k"的具体建议
- Phase 0 默认禁用 ✅
- $35k 资金量看似够,但**经验不够**
- Phase 1 阶段(资金量稳定 $50k+,运行 6+ 月后):
  - 启用监控模式

## 四、回测与上线门槛(2 项)

### **决策 4.1 · 回测必须达到 Sharpe > 1.5、Max DD < 8%、WinRate > 70%**

#### 是什么
每个策略**必须先在 12-24 个月历史数据上回测**,达到 3 个标准才能进入 Paper Trading 阶段。

#### 关键数字

| 指标 | 标准 | 含义 |
|---|---|---|
| **Sharpe 比率** | > 1.5 | 收益相对风险的"性价比" |
| **Max Drawdown** | < 8% | 历史最大亏损不超 8% |
| **Win Rate** | > 70% | 70%+ 的交易盈利 |
| **年化收益** | > 15% | 至少高过储蓄收益 |
| **样本外测试** | Out-of-sample 也通过 | 防过拟合 |

#### 为什么这样设计

**Sharpe > 1.5**:
- 顶级 quant 基金长期 Sharpe 0.8-1.2
- 我们要 1.5 是因为:**回测高估实盘 0.5**
- 回测 1.5 → 实盘大概率 1.0
- 回测 1.0 → 实盘大概率 0.5(不值得做)

**Max DD < 8%**:
- 8% 是心理可承受的上限
- 超过 8% 你会做错决策(早平仓 / 加仓 / 改参数)

**Win Rate > 70%**:
- Delta 中性策略本来就该高胜率
- 低于 70% 说明策略有 bug 或对冲不完整

#### 不同意的后果

**降低标准(Sharpe > 1.0)**:
- 回测 1.0 → 实盘 0.5 → **几乎无利可图**
- 长期累积亏损 + 时间成本

**完全跳过回测**:
- 实盘第一周必出大问题
- 这是该行业 95% 失败者的共同特征

**提高标准(Sharpe > 2.0)**:
- 几乎没有策略能达到
- 你会"过度优化"参数 → 严重过拟合 → 实盘归零

#### 替代方案
- **更宽松**:Sharpe > 1.0 → 我**强烈反对**
- **加额外指标**:Calmar、Sortino → 复杂化,Phase 2 再加

#### 给"全职 + $35k"的具体建议
- 接受这 3 个标准
- 知道你会**多次失败**:
  - 第一次回测可能 Sharpe 0.8,需要调参数
  - 调完可能过拟合(in-sample 1.8, out-of-sample 0.6)
  - 重新设计 → 重新回测
  - 总共可能 2-3 周
- 这个"多次失败"是**正常的、健康的**

### **决策 4.2 · Paper Trading 至少 14 天才能进实盘**

#### 是什么
回测过了之后**不能直接实盘**。必须用**实时行情 + 模拟订单**跑 14 天,验证执行链路。

#### 关键数字

```
Paper Trading 阶段:
  时长:14-30 天
  数据:真实行情(WS 推送)
  订单:模拟成交(不真实下单)
  目标:发现回测发现不了的"工程问题"

必须验证:
  - WebSocket 断连是否能恢复
  - 订单失败时是否能正确处理
  - 多策略并行时资源分配是否对
  - 凌晨结算时系统是否稳定
  - 跨时区跨交易所时序问题
```

#### 为什么这样设计

**回测验证"理论"**:
- 历史数据 + 模拟执行
- 发现不了延迟、滑点、API 限流等"现实问题"

**Paper Trading 验证"工程"**:
- 真实环境 + 模拟订单
- 暴露所有现实世界的边界情况
- 例:Binance 凌晨 4 点的资金费结算时间窗口
- 例:WS 断连后 30 秒内没收到推送
- 例:某币种突然暴涨,订单簿深度不够

**14 天是为什么**:
- 7 天太短,只能跑 1 个完整 funding 周期
- 14 天 = 2 个 funding 周期 + 一个完整周末
- 30 天理想,但时间成本太高

#### 不同意的后果

**跳过 Paper Trading**:
- 实盘第一周必出问题(80% 概率)
- 真金白银亏损 → 心态崩 → 早期放弃

**Paper 7 天**:
- 可能第 8 天才暴露问题
- 不充分

**Paper 30 天**:
- 更稳,但拖慢整体进度
- Phase 0 时间被压缩

#### 替代方案
- **Paper 7 天**:只在策略简单时(如三角套利)可以
- **Paper 30+ 天**:对复杂策略(如配对交易)推荐

#### 给"全职 + $35k"的具体建议
- 接受 14 天
- 第 7 天做一次 mid-review
- 如果 Paper 表现 ≠ 回测预期(差距 > 30%),**重新回测**
- 不要"凑够 14 天直接上"

## 五、安全与边界(2 项)

### **决策 5.1 · 多用户授权层 = 白名单 + 完全免费**

#### 是什么
第 12 章设计的多用户系统**只给你认识的朋友用**:
- 白名单注册(邀请码制)
- 完全免费(不收任何费用)
- 不公开广告 / 不公开注册
- 不做客服(出问题用户自己解决)

#### 关键数字

```
白名单模式:
  法律风险:0(免费 + 私人项目)
  合规成本:0
  起步成本:0

商业化模式(SaaS):
  法律风险:高(虚拟资产相关业务)
  合规成本:$460k+ 起(律师 + MSB 牌照 + 反洗钱系统)
  时间成本:6-12 个月
  失败概率:90%(独立开发者)
```

#### 为什么这样设计

**法律边界**:
- 你帮朋友"无偿管理代码" = 私人协议,无监管
- 你"收费提供策略系统给朋友" = 投顾业务,大多数司法管辖区需要牌照
- 你"运营 SaaS 让陌生人接交易所 API" = 高度受监管

**操作边界**:
- 1 个用户(你自己):你能调试任何 bug
- 5 个朋友:出问题大家电话商量,3 天解决
- 100 个用户:每天都有人 ticket,你光做客服没时间开发
- 1000+ 用户:必须组建团队 / 法务 / 合规

**心理边界**:
- 朋友亏钱:他们知道是测试,不会怪你
- 陌生人亏钱:可能告你

#### 不同意的后果

**如果你想商业化**:
- **必须先做合规**(找律师 / 注册公司 / 申请牌照)
- 不合规收费 = 个人刑事责任
- 起步成本至少 $460k(详见第 12 章末尾分析)
- **你 $35k 资金根本不够**

**如果你想公开免费**:
- 比白名单灵活一点,但仍有客服压力
- 一旦"系统出 bug 用户损失",你可能被告
- 即使免费,某些司法区也认为是"无证投顾"

#### 替代方案
- **公开免费(无白名单)**:风险中等,**不推荐**
- **付费但匿名(无客户协议)**:风险**极高**,绝对不行
- **白名单 + 收朋友"维护费"**:边界模糊,**不推荐**

#### 给"全职 + $35k"的具体建议
- 接受白名单 + 完全免费
- 朋友用完后如果想感谢你,**让他们请吃饭**,**不要收钱转账**
- 1 年后如果你想商业化:那时你有运营数据 + 现金流,可以聘请律师正式做

### **决策 5.2 · 多用户授权层是 Phase 2(核心系统稳定 3 个月后才做)**

#### 是什么
第 12 章设计的多用户系统**不在开发计划的前 12 周里**。

先做单租户系统稳定运行 **3 个月**,再做多用户。

#### 关键数字

```
开发顺序:
  Week 1-12 (Phase 0):  单租户(只有你自己)
  Week 13-24:           Phase 0 → Phase 1 过渡(还是只有你)
  Week 25-36:           核心系统稳定 3 个月
  Week 37+ (Phase 2):    开始做多用户

预计:
  最早第 9 个月(36+ 周后)朋友才能用上
```

#### 为什么这样设计

**多用户层会让你的工作量翻倍**:
- 用户认证、权限、邀请码 → 1 周
- API key 三层加密 → 1 周
- 数据隔离(per-user position / orders) → 2 周
- 用户管理 UI → 1 周
- 测试 + 调试 → 2 周
- **总共 1.5-2 个月**

**如果你同时做多用户 + 自己策略**:
- 你前 6 个月几乎全在救火
- 朋友催 → 你压力大 → 决策错误
- 自己策略亏 → 朋友也亏 → 关系破裂

**等单租户稳定 3 个月**:
- 证明系统已经可靠
- 你有真实运营数据
- 风控参数已经验证过
- 这时给朋友用,他们的钱才安全

#### 不同意的后果

**如果你想前 12 周就做多用户**:
- 前 6 个月你**两件事都做不好**
- 多用户系统有 bug → 朋友资金安全风险
- 自己策略受影响 → 自己也亏

**如果你 1 年后才做**:
- 朋友等不及,失去兴趣
- 但风险最低

#### 替代方案
- **同时做**:**强烈反对**
- **半年后做**:可以,但前提是单租户在第 6 个月稳定
- **不做**:更省事,但失去 multi-user 价值

#### 给"全职 + $35k"的具体建议

- **现在告诉你的朋友**:"我 9 个月后再做多用户系统"

- 不要因为"朋友催"就提前做
